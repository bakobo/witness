# A witness started over a volume with NO KEYSTORE silently creates one, and every black-box signal says it is healthy. Measured 2026-09-05 while building infra's tier-one restore drill: delete ks/ from a volume, start the container, and it reports {"status": "ok"}, serves the ORIGINAL AID from the database's hab record, accepts a controller inception over HTTP with a 204, and `witness backup` succeeds. That is @7kwmhg's disaster wearing a green light -- the same AID every validator still trusts, against a signing key that is not the one that AID names. A restore from a keystore-less backup produces exactly this and nothing tells the operator. Suggested: refuse to start when the keystore is absent but the database holds a hab, since that combination cannot be legitimate; at minimum surface it in /v1/witness/health, which currently cannot distinguish it from healthy. infra's drill now asserts on the restored TREE before starting anything, because it could not be inferred from the running container.
