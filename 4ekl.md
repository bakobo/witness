# Measure the query-not-found escrow cost before claiming anything about it (SEC-F1, and docs/deploying.md says the same). Kevery.processQueryNotFound re-walks the whole qnfs table every hio pass; sustaining N entries costs an attacker ~N/300 req/s on the publicly-proxied port, unauthenticated. Bounded by TimeoutQNF=300s so it drains, but the per-pass cost degrades the single-threaded loop the whole design protects. Wanted: a latency-versus-query-rate curve. Until that exists this is a code reading, and per the standing rule nothing goes upstream to WebOfTrust without it. Compensating control (edge rate limiting) lives in infra and is unconfirmed.

- 2026-09-04T15:58Z Done 2026-09-04. Measured curve in docs/escrow-load.md; harness tests/test_escrow_load.py (gated on WITNESS_LOAD, ~7min). Cost is LINEAR at ~0.35ms per escrowed entry per hio pass, paid by WitnessStart — the same doer that ingests and receipts real events. At 200 entries a controller is witnessed in 0.075s vs 0.046s baseline; at 1000 entries 0.257s, loop lag 0.33s against a 0.03125s tock. Two things the arithmetic did not give: degradation starts UNDER 1 req/s (~200 entries), one to two orders of magnitude below the '10k entries at 33 req/s' framing, so a per-source rate limit loose enough for legitimate traffic still admits it; and it DRAINS (depth fell 1000->823 while the flood continued), so a flood that stops is a witness that recovers unattended. Alert threshold now defensible: witness.loop.lag > 0.05s sustained 1min, read alongside witness.escrow.depth{store=query_not_found}. Health reports ok at 0.33s lag and that is correct — pinned by a test so nobody 'fixes' it. Still hardening, not a defect: TimeoutQNF exists to bound it and does. NOT reported upstream; per the standing rule Daniel posts to WebOfTrust.
