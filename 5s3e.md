# keripy read-only Baser open CREATES a phantom empty env on a MISSING DB (and pollutes ~/.keri under the default head) — readonly does not prevent creation. Guard by checking data.mdb at resolved candidate paths before opening (pattern: reader._resolve_existing_db). Reuse for the runner and any future keripy DB reader; do not trust hio Filer.exists (checks dir, not data.mdb; alt-path fallback).

- 2026-09-03T22:50Z Root cause found 2026-09-03 and fixed in reader.py: keripy silently DISCARDS Baser(readonly=True) when reopen=True. LMDBer.__init__ consumes readonly and sets self.readonly, Filer.__init__ then calls reopen() without it, and LMDBer.reopen's readonly=False default overwrites it — the 'if readonly is not None' guard can never be False. So the env opened read-WRITE, which is why a 'read-only' open could create a phantom DB. Fix here: construct with reopen=False, then rdb.reopen(readonly=True); verified the env now refuses write txns and still registers in the lock table. The _resolve_existing_db guard is now belt-and-braces rather than the only defence, and is worth keeping for the typed error. Upstream fix would be one line: LMDBer.reopen(self, readonly=None, ...). NOT reported to WebOfTrust — Daniel posts those.
