# In-loop per-doer timings via a publish-only hook doer, so a wedged witness names the doer that wedged it. Witnesses have wedged in production, and black-box probing of the witness HTTP port only detects THAT the loop stalled; per-doer timings say WHICH doer, which is what a fix or an upstream report needs. Reachable only from inside the Doist: setupWitness returns its doers list and runController builds the Doist internally (keri/app/directing.py:635), so this requires the launcher (@n5r2vq) and gives up stock 'kli witness start' (@tdd36d). Deferred behind P1/P2 by Daniel 2026-09-03: connection counts (/proc/net/tcp in the shared netns), throughput (LMDB first-seen deltas) and liveness (black-box probe, which beats a self-reported heartbeat because our separate process can answer WHILE the witness is wedged) all need no hook, so timings are the only signal that does. HARD CONSTRAINT if built: the in-loop doer publishes, never computes — stores into a pre-mapped fixed-size segment, no allocation, no I/O, no LMDB, no branching on external input, frozen by a test not a note, or the 'just one more small doer' ratchet lands us in-process by accretion. Channel: evaluate hio Boss/Crew multidoing first (see ~5gsx, same question from the control direction) before a bespoke mmap segment; a purpose-built telemetry segment CAN be mapped PROT_READ by the control plane, unlike the LMDB it was originally proposed for (see .ignored/lmdb-two-container-analysis.md).
